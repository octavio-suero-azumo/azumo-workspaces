## 2. Components

```
Browser (React client components: editor, upload widget)
   │  server actions / fetch
Next.js server (Vercel Functions)
   ├─ middleware.ts            optimistic redirect to /sign-in only (NOT authorization); Next 16 may name it proxy.ts, so verify in T-01
   ├─ src/server/env.ts        typed env validation, fail-closed (R1.3)
   ├─ src/server/auth/         Better Auth config, Google provider, domain guard hook
   ├─ src/server/authz/        permissions.ts (role→action map), authorize.ts (single helper)
   ├─ src/server/data/         workspace-scoped data access (only place that imports db)
   ├─ src/server/db/           Drizzle schema + client
   ├─ src/app/**               pages + server actions (call data layer only)
   ├─ src/app/api/uploads      Blob token route (uploads only)
   └─ src/app/api/files/[id]   authorizing download route (uploads only)
External: Google OIDC · Neon Postgres · Vercel Blob (uploads only)
```

Data flow rule: UI → server action or route handler → `requireSession()` → `authorize()` → `src/server/data/*` → DB. Components never touch the DB (AC-12).

## 3. Entities and relations

The Better Auth tables `user`, `session`, `account` and `verification` are generated by its CLI. `user.email` is unique, and the table includes `email_verified`, `name` and `image`.

**Note (developer inconsistency 3, reviewer RV-20):** Better Auth defaults to text IDs and camelCase columns, which may not match the uuid and snake_case notation below. T-03a pins one ID and column-name strategy, so that FKs to `user.id` get compatible types.

| Table | Fields | Keys and constraints |
|---|---|---|
| `workspace` | `id` uuid, `name` text, `created_by`, `created_at`, `updated_at` | PK `id`. `name` length 1–100 (CHECK). FK `created_by` → `user.id` |
| `membership` | `id` uuid, `workspace_id`, `user_id`, `role` text, `created_at` | PK `id`. **UNIQUE(`workspace_id`, `user_id`)**. `role` CHECK IN (configured set, PR3). FKs cascade on workspace/user delete. Index `user_id` |
| `page` | `id` uuid, `workspace_id`, `title` text, `content` jsonb null, `created_by`, `updated_by`, `created_at`, `updated_at` | PK `id`. **UNIQUE(`id`, `workspace_id`)** (target for the composite FK). FK `workspace_id` cascade. `title` length 1–200. Index `workspace_id` |
| `attachment` | `id` uuid, `page_id`, `workspace_id`, `kind` text, `display_name`, `url` null, `blob_pathname` null, `content_type` null, `size_bytes` null, `created_by`, `created_at` | PK `id`. **FK (`page_id`, `workspace_id`) → page(`id`, `workspace_id`)** ON DELETE CASCADE (AC-25). `kind` CHECK IN (values allowed by P2). CHECK: `kind='link'` requires `url` and forbids `blob_pathname`; `kind='upload'` is the reverse. `blob_pathname` UNIQUE |

Relations: user 1–N membership N–1 workspace. workspace 1–N page 1–N attachment. `attachment.workspace_id` is denormalized so every query can filter directly by workspace, and the composite FK keeps it consistent.

## 4. Server-side authorization

1. **`requireSession()`** reads the Better Auth session on the server and throws `Unauthenticated` (mapped to 401 or a redirect) if there is none.
2. **`authorize(ctx, target, action)`** is the only authorization entry point. `target` is `{workspaceId}`, `{pageId}`, `{attachmentId}` or `{membershipId}`. When the request carries a resource ID, `workspace_id` is **never taken from client input**: it is resolved from the resource row (RV-07). It runs **one query** that joins the resource to `membership` on `membership.workspace_id = resource.workspace_id AND membership.user_id = ctx.userId`.
   - No row: throws `NotFound` (404, DP2). Non-members can't tell whether the resource exists.
   - Row found but `can(role, action)` is false: throws `Forbidden` (403).
   - Otherwise it returns `{ workspaceId, role, resource }`.
3. **`can(role, action)`** in `permissions.ts` is a pure lookup table (§5). If PR3 changes, this table and the `role` CHECK are the only places to edit.
4. **Query scoping:** every function in `src/server/data/*` takes `ctx`. Reads join through `membership` for `ctx.userId`. Writes include `WHERE workspace_id = <authorized workspaceId>` (and `id = …`), so a substituted ID from another workspace affects 0 rows.
5. Middleware only redirects when there's no session cookie. It is **never** relied on for authorization, following Vercel's guidance to check auth in the handler.
6. Errors are mapped to HTTP status in one place (`src/server/http.ts`). Responses never include stack traces or foreign data.
7. The UI calls the same `can()` to hide controls (R3.4). The server still enforces every action.
8. **Server actions** are public POST endpoints. All of them go through a single `action()` wrapper that calls `requireSession()`, and a static test checks that no server action skips it (RV-06, AC-01).
9. **No session or role caching:** Better Auth `session.cookieCache` is disabled. Membership and role are read from the DB on every request and never stored in the session (RV-06, AC-07, AC-37).
10. **Last-Owner guard (DP3):** implemented as a single conditional `UPDATE`/`DELETE … WHERE` with a subquery that counts the remaining Owners. It needs no interactive transaction, so it doesn't constrain the choice of Neon driver (RV-16).

## 6. Auth flow and domain check (R1)

1. `/sign-in` calls Better Auth's Google sign-in. The `hd` request parameter only filters the account picker; it isn't a control.
2. Google redirects to `/api/auth/callback/google` (exact redirect URI per environment).
3. Better Auth verifies the ID token and **rejects tokens whose `hd` claim ≠ `ALLOWED_GOOGLE_HD`**, including tokens with no `hd`.
4. A defensive guard rejects the sign-in unless `email_verified === true` **and** `hd === ALLOWED_GOOGLE_HD`, and writes no row on rejection (AC-03 to AC-05). The guard runs before user creation **and** before session creation, because returning users skip user creation (developer RK-1). Whether it also checks the email's own domain is **pending P1**; secondary-domain users could get `hd` from the primary domain (RV-01). Where the `hd` claim is available (for example `mapProfileToUser`, never a custom `getUserInfo`) is verified by a spike in T-06a.
5. `env.ts` validates at startup: `ALLOWED_GOOGLE_HD` must be a non-empty hostname and not `*`. Otherwise it throws, and the app fails closed (R1.3).
6. If P1 resolves to more than one domain, steps 3–5 need custom multi-value validation. That is a change to T-06a and must be approved first.

## 7. File handling per P2

| Option | Design |
|---|---|
| **Link** | A server action does `authorize(page, attachment.add)`, then parses with `new URL()`. It requires `https:` and length ≤ 2048 (DP6) and stores `kind='link'`. The server never fetches the URL, so there is no SSRF. Links render with `target="_blank" rel="noopener noreferrer"`. |
| **Upload** | *Store:* a **private** Blob store (access mode can't be changed later). *Token:* `POST /api/uploads` uses `handleUpload`. `onBeforeGenerateToken` runs `requireSession`, reads `pageId` from `clientPayload`, runs `authorize(page, attachment.add)`, sets `allowedContentTypes` and `maximumSizeInBytes` (P8), and **validates** that the pathname starts with `ws/{workspaceId}/pg/{pageId}/`, rejecting it otherwise. Whether the server can rewrite the pathname instead is unverified, so T-15 checks it (RV-08). *Register:* `onUploadCompleted` doesn't reach localhost, so after the upload the client calls the `registerUpload(pageId, pathname)` server action. That action re-authorizes, checks the prefix matches the authorized workspace and page, calls `head()` to confirm the blob exists and read its size and type, and inserts the row. *Download:* `GET /api/files/[attachmentId]` runs `authorize(attachment, page.view)`, then `get()`, and streams with `Cache-Control: private, no-cache`, `Content-Disposition: attachment` (DP7; the filename comes from `display_name`, encoded per RFC 6266) and `nosniff`. *Delete:* removes the row, then `del()` the blob. Uploads stay below the 4.5 MB function limit because they go straight from the client to Blob. |
| **Both** | The union of the two. `kind` CHECK allows both values, and the UI has two entry points. |

## 9. Security notes

- Authorization happens only on the server, through `authorize()`. Hiding UI is never enforcement.
- Cross-workspace isolation comes from membership joins, write filters on `workspace_id`, and the composite FK on attachments.
- IDs are random UUIDs. That makes them hard to guess, but authorization doesn't depend on it.
- The test auth module has no HTTP route and is imported only by test setup. Production enables only the Google provider (AC-36). Playwright's `storageState` directory is gitignored.
- Editor content is rendered only through the editor's schema. No raw HTML injection.
- CSRF: rely on Next.js server action origin checks and Better Auth's built-in protections. Route handlers that change state accept only POST/DELETE with a session.
- Next.js patch releases are frequent (research §4). Pin the version and re-check before deploying.
- Never use BlockNote `xl-*` or Tiptap Pro packages (licensing).
- The connected Vercel and Gmail MCP servers must not be used to deploy or send anything without explicit per-use authorization (agent-check reviewer finding 2).
